# Meld2: bounded caching on a real Bun/OpenNext workspace

Meld2 is a Bun workspace, not an independently installable Next.js app. Its
API app uses Next 16.3.5 and OpenNext Cloudflare 1.20.6, with a local workspace
package and a frontend asset-sync step. The measured command is the project's
actual `bun run --cwd apps/api opennext`: it synchronizes assets, runs Next,
and packages the Cloudflare worker. No deployment command was executed. This
three-snapshot study used the earlier checkout, before the static `candidate/`
frontend was replaced by the React application in `apps/web`; the historical
retention percentages are not a measurement of the current React application.

## Initial state and scope

The inspected checkout had no installed dependencies, `.next` output, or shared
nanocompile cache. There was therefore **no existing build cache to shrink**.
Its source/design assets were not deleted, rewritten or compressed. In particular,
review assets are application/design material, not disposable compiler cache.

A frozen Bun installation and the project's own checks/tests preceded a real
OpenNext build. That initial build generated these separate categories:

| Category | Logical bytes |
| --- | ---: |
| Installed root dependencies | 1,079,796,487 |
| Task-local Bun download cache | 951,630,359 |
| Entire Next output, including its cache | 255,128,684 |
| Next compiler-cache directory | 147,418,992 |
| Packaged OpenNext output | 63,355,425 |
| Synced frontend output | 7,834,349 |

Rows are not additive: the Next cache is already part of the Next output.
Allocated-block counts can also double-count hard links or shared filesystem
clones; they are not a measurement of unique physical disk allocation.
Installation and build outputs increase total checkout storage from its initially
unbuilt state. A smaller retained shared cache is not a smaller app bundle.

## Integration used

The workspace adds `tools/nanocompile-build.py`, exposed as `bun run build:cached`.
It requires a current ReleaseSafe CLI with automatic budget support and its
installed Python helpers. It does not claim that the standalone worktree
preparer can infer a Bun monorepo's install graph.

The adapter always runs the real OpenNext build. It shares only quiescent
SWC/Webpack hints and the exact native Turbopack engine directory
`v16.3.5-ca2c75eb`; it never replays `.open-next`, rendered outputs or fetch data.
The compatibility key conservatively includes workspace source content,
workspace manifests, the root lockfile/configuration/patches, environment digests,
Node/Bun identity, Git build identity and the adapter itself. This initial
integration targets unchanged-checkout reuse, not inferred cross-source-edit
monorepo portability. Ignored environment files are digested, not copied into
reports. Existing mutable local caches are preserved.

The study's project-private shared store is `.cache/nanocompile`, with a
**192 MiB** (201,326,592-byte) retention budget: enough for the measured
approximately 140 MiB snapshot, without retaining several obsolete full snapshots.
The current React-workspace adapter instead uses **384 MiB** (402,653,184 bytes),
because its first real snapshot was 281,589,760 bytes and correctly did not fit
the historical budget. See the current-workspace verification below. The
project's `.cache` tree is ignored. Dependencies, package downloads and local
Next/OpenNext outputs remain separate categories, not silently included in
this limit.

## Measurement method

Three actual completed build snapshots are archived with normalized metadata.
The same archive bytes are stored in two isolated native CAS stores: a 1 TiB
baseline (effectively no eviction for this study), and the 192 MiB bounded store.
The baseline is explicitly not `NANOCOMPILE_MAX_SIZE=0`, which means retain
nothing. Each store receives the same workload and artifact identity; overwritten
snapshot blobs accumulate in the large-budget baseline unless collected.
Every native artifact roundtrip must match the original archive bytes.

Before the third real build, only the compiler directories generated by this
study are moved aside under the worktree lock. The adapter must report a seed
restore from the bounded store, then complete another real OpenNext build.
Source assets and dependencies are not removed. Temporary comparison stores,
archives and held compiler directories are removed after successful verification;
private build logs and raw measurements are not copied into public artifacts.

## Results

| Completed real snapshot | Archive bytes | Baseline entries + blobs | Bounded entries + blobs |
| --- | ---: | ---: | ---: |
| First | 146,483,200 | 146,483,696 | 146,483,696 |
| Second | 147,804,160 | 294,287,856 | 147,804,656 |
| Third, after a bounded-store seed restore | 148,930,560 | 443,218,416 | 148,931,056 |

The same three-build workload retained **294,287,360 fewer logical bytes
(66.4%)** in the bounded store. All three native archive roundtrips were
byte-identical. The restored third build completed successfully and retained
its refreshed snapshot. This is useful retention with eviction, not compression
of individual files or a smaller deployment bundle.

The baseline OpenNext command took 15.81 seconds. The later real builds took
9.80 and 9.68 seconds inside the adapter; the latter used the restored seed.
These are single observations with different warm states, **not a controlled
speedup claim**. A final `bun run build:cached --local-fixture-env` invocation
also passed using the project-private ReleaseSafe installation, after adapter
updates and removal of the study's package-download cache.

The task-created Bun download directory was removed after confirming installed
dependencies did not reference it: 951,630,359 logical bytes no longer remain
in that separate directory. Installed dependencies were preserved, and the final
real build still passed. This was a one-time cleanup, not automatic eviction of
package-manager downloads; no unique physical-byte savings are claimed.

Sanitized aggregate evidence is in [`../benchmarks/meld2-cache.json`](../benchmarks/meld2-cache.json).
Raw logs, compatibility keys, archive fingerprints and app-derived payloads stay
private. The comparison stores and temporary archives were removed; the useful
bounded store and local compiler outputs remain.

## Reproduce the integrated command

From Meld2's root, install the updated nanocompile source into a project-private
prefix (use the actual path to your nanocompile source checkout):

```sh
MELD_ROOT="$PWD"
(cd /path/to/nanocompile &&
  zig build -Doptimize=ReleaseSafe --prefix "$MELD_ROOT/.cache/nanocompile-cli")
bun install --frozen-lockfile
bun run check
bun run --cwd apps/api test
bun run build:cached --local-fixture-env
```

The adapter prefers `.cache/nanocompile-cli/bin/nanocompile`, with
`NANOCOMPILE_BIN` as an explicit override, then falls back to `PATH`. Its installed
Python helpers are required. Check `--help` for `NANOCOMPILE_MAX_SIZE`: the
previous public v0.1.0 release does not contain this local automatic-budget work,
even though the source version string remains the same. These integrations and
measurements have not been published as a new release.

The fixture option supplies non-production build-only configuration with no live
database access. **Do not deploy its generated worker/output.** Rebuild using the
actual deployment configuration before shipping. For the caller's normal
environment, omit that flag:

```sh
bun run build:cached
# Inspect the same project-private store with the same retention budget:
NANOCOMPILE_DIR="$PWD/.cache/nanocompile" \
NANOCOMPILE_MAX_SIZE=402653184 \
  ./.cache/nanocompile-cli/bin/nanocompile stats
```

`--max-size` overrides the byte budget for an invocation. Keep the setting
consistent for cooperating processes; `0` means retain nothing, not unlimited.
The current 384 MiB policy bounds settled native entries/blobs, not temporary peak writes,
installed CLI files, dependencies, downloads, or `.next`/`.open-next` outputs.
Meld2's `docs/nanocompile.md` and root `SKILL.md` describe its workspace-specific
adapter; this repository's [`../SKILL.md`](../SKILL.md) is reusable guidance.

## Current React-workspace verification

The integration was subsequently updated to current Meld2 `main`, preserving the
new workspace scripts. Its conservative contract includes all apps, packages,
build tools/patches, root manifests/configuration and ignored environment files
across workspace roots. Owned frontend/tool probes and ignored frontend-env
probes proved same-size edits invalidate the key; removing the probes restored
the original key. No application source was changed for these checks.

Node.js 24 and Bun 1.4.2 were used for a frozen install and successful
`bun run check` and `bun run test`. The Vitest suites reported 389 extension,
1,509 API and 1,307 frontend tests passing; 201 API tests were skipped, not
claimed as live-service passes. An initial test run incorrectly supplied
build-fixture origin variables; a clean test environment passed without changing
application tests or code.

With the new 384 MiB budget, a real build retained a seed, then a subsequent
build reported `cache: restored`, completed React/Vite and OpenNext packaging,
and retained its refreshed snapshot. Final managed entries/blobs were
**284,180,976 logical bytes**, within the 402,653,184-byte limit. Observed build
phases were 11.14 and 11.26 seconds, not a controlled speedup comparison.
The held study-generated compiler directories were removed after success.

[Current-workspace aggregate evidence](../benchmarks/meld2-current-main.json)
is separate from the historical three-snapshot retention study. This verifies
useful bounded caching on the updated application, not a new 66.4% savings claim.
No browser/live-service acceptance, deployment or migration was performed.

# Complete, focused inputs for declared tasks

A useful task contract includes **everything the task can observe that affects its output**, not everything tracked by Git. Excluding `docs/` from a repository-wide list is not evidence that the remaining list is complete. Conversely, declaring only `src/` is unsafe when a build also reads configuration, scripts, generated files, package contents, or runtime resources.

This is a worked example for the [experimental declared-file task runner](declared-tasks.md), not automatic dependency discovery. The executable implementation is [`tests/focused_task_inputs.py`](../tests/focused_task_inputs.py); it uses only Python's standard library and creates its project and private cache in a temporary directory:

```sh
python3 tests/focused_task_inputs.py /absolute/path/to/nanocompile
# From a checkout with a current build:
python3 tests/focused_task_inputs.py zig-out/bin/nanocompile
```

The five tests run real deterministic programs, remove outputs before **every** cache invocation, check per-task hit/miss events, and compare all restored/generated bytes with fresh uncached executions. There is no test-only execution log in the child programs and no network, package manager, or compiler prerequisite beyond Python and nanocompile. The fixture uses the default strict task schema; it does not opt into relocation.

## The example's complete contract

The fixture builds a deterministic binary bundle rather than pretending to discover an arbitrary language's dependencies. Its two programs import only the built-in `sys` module. Each receives its exact read list as command arguments, serializes each input's name, byte length, and bytes, and writes one named output. A version marker in each program also contributes to the result. Reading a lockfile or configuration here means bundling its bytes; this is not a lockfile resolver or configuration parser.

```text
scripts/generate.py                 generator program
scripts/build.py                    bundle builder
schema/model.txt                    generator input
src/{main,optional}.txt              application sources
config/build.json                   build configuration
deps.lock                           dependency resolution record
vendor/demo/{package.json,payload.txt}  installed dependency files
generated-external/vendor.inc       generated source supplied before discovery
tool/banner.txt                     installed tool data read by the builder
docs/guide.md                       not read by either program
out/model.txt                       generator output, builder input
out/artifact.bin                    final output
```

`FocusedInputs.discover()` constructs the entire schema-1 specification before each invocation. The specification has these two tasks, in this order:

| Field | `generate` | `build` |
| --- | --- | --- |
| `command` | Absolute Python executable, `-I -S -B`, `scripts/generate.py`, output filename, sorted schema members | Same executable/flags, `scripts/build.py`, output filename, ordered build data members, `tool/banner.txt` |
| `inputs` | `scripts/generate.py`, every file under `schema/` | `scripts/build.py`, every file under `src/` and `config/`, `deps.lock`, every file under `vendor/` and `generated-external/`, `out/model.txt` |
| `outputs` | `out/model.txt` | `out/artifact.bin` |
| `depends_on` | Empty | `["generate"]` |
| `tool_resources` | Installed Python startup resources | The same resources plus `tool/banner.txt` |
| `cwd` | Default `.` | Default `.` |

The implementation supplies **individual existing file paths**, not directory inputs or wildcard strings. Each root's members are sorted, and root order is stable. The corresponding command arguments also record exactly which members the program reads. The scripts themselves are project inputs: executable selection alone does not fingerprint a script passed to an interpreter.

The builder's generated input `out/model.txt` is declared in `inputs` **as well as** its producer in `depends_on`. Ordering alone is not a data dependency. The producer creates/restores that file before the consumer's input hashes are taken, so the file need not exist before the overall graph starts. For externally supplied generated sources, the caller must finish generating them before discovery and include their files. If that generation is also to be cached, give it a task with its own complete script, configuration, source, and tool contract.

Both the lock and the actual installed package bytes are included. A lockfile can remain unchanged while an installed package is patched, corrupted, or replaced. In a real project include imported/transitive packages, package manifests, build-time plugins, headers, schemas, templates, and package data actually reachable by the build. Do not substitute a lockfile for those bytes unless a separate verified mechanism establishes the exact immutable package installation.

### Installed runtime and host assumptions

The interpreter executable is selected and fingerprinted by nanocompile. The fixture additionally probes the isolated interpreter's startup modules and declares their existing source/bytecode files plus the Python shared library at conventional installation locations as `tool_resources`. It runs with `-I -S -B`: no user site, `PYTHONPATH` imports, automatic `site` import, or bytecode writes. The programs import no extra libraries. This is a bounded runtime contract for these particular programs, **not a general Python dependency scanner**.

The fixture assumes a conventional, trusted Python installation and a stable native host runtime, including the OS loader and system libraries. For a custom Python distribution, embedded runtime, unusual shared-library layout, or additional imports, extend `python_resources()` with the actual runtime/library/data closure before relying on it. The probe does not discover arbitrary future/dynamic imports or native loader dependencies. A compiler build likewise needs its support executables, runtime libraries, plugins, target data, and other installed resources, not merely the compiler launcher.

Installed resources use the runner's trusted-installation metadata identity policy. They are not a safe category for frequently edited project files or same-metadata rewrites: put those files in `inputs` for fresh complete content hashing. The resource test replaces `tool/banner.txt` with a different-sized version. If an installation change can escape its identity assumptions, declare the affected resources appropriately or clear this experimental cache. Do not infer that the host OS/CPU key fields fingerprint every system library.

The task keys also include command arguments, working directory, environment and host safeguards. Tests keep those stable across invocations and use a private cache. The programs do not read clocks, randomness, filesystem metadata, undeclared configuration, network services, or directory listings. The latter belongs solely to caller-side discovery. Whole-task caching is not a sandbox that enforces these assumptions.

## File membership is an input too

`members(root, directory)` is caller-owned discovery. It recursively lists **all** files under the selected roots without extension filters, including untracked files. It rejects symlinks and special files in those trees. The fixture supplies ordinary directories and regular files; supporting symlink targets, metadata-sensitive builds, or different directory semantics requires an additional explicit policy.

Discovery is rerun before every invocation, including anticipated hits. An added file enters the ordered `inputs` and command lists; a deleted file leaves them. An empty file addition changes output because the bundle encodes names. The task key therefore represents membership, not just the hashes of yesterday's files. Keeping a stale list is unsafe: an omitted addition could produce a false hit, while retaining a deleted input generally produces a validation/read failure rather than a useful rebuild.

The test adds a member, then deletes a different original member, so both resulting contracts are new and must miss. Deleting the newly added member instead would return to an already cached contract; a hit would be correct in that case. All surviving files remain readable, and every changed artifact is compared against uncached output.

In a real build, derive this set from dependency evidence: compiler depfiles, a package graph and verified installation, build-system metadata, explicit manifests, or a deliberately bounded filesystem read model like this example. Account for optional-file existence checks, import search paths, include precedence, directory scans and generated-file discovery. Re-run discovery or record a complete membership manifest when such choices can change. A negative lookup cannot be represented by listing a nonexistent file as an existing-file input; caller-side discovery must translate the current choice into a changed contract or another deterministic declared input. Do not recursively hash the task's own outputs as source inputs.

The caller must also provide a stable source/package snapshot from discovery through execution. The runner revalidates declared input bytes, tool identities and specification bytes, but cannot detect a new **undeclared** file appearing after discovery. If concurrent edits are possible, serialize discovery/build against them, use immutable snapshots, or validate membership externally before accepting a result. An exclusion list alone does none of this.

## What the executable checks

Every row below also verifies byte equality against the direct, uncached task graph. Source/dependency membership tests and content tests verify that the final artifact actually changes, not merely that the runner reports a miss.

| Change after a cold `miss / miss` | Expected `generate / build` |
| --- | --- |
| Edit, add, or remove unrelated documentation | `hit / hit`, identical output |
| Edit application source or build configuration | `hit / miss` |
| Edit the dependency lock | `hit / miss` |
| Edit installed package manifest or contents without changing the lock | `hit / miss` |
| Edit externally generated source | `hit / miss` |
| Change builder script's output marker | `hit / miss` |
| Change generator script's output marker or schema bytes | `miss / miss`, changed generated and final output |
| Replace declared installed tool data | `hit / miss` |
| Add/delete source, config, package, or externally generated members | `hit / miss` |
| Add/delete schema members | `miss / miss` |
| Repeat a completed changed contract | `hit / hit` |

Documentation is absent because these programs provably never read it, not because Markdown is universally safe to exclude. A documentation generator, embedded README, license bundler, or version script could make those same files build inputs. Before narrowing another build's contract, reproduce the same validation pattern: establish the read closure, regenerate membership, delete outputs, verify hits/misses, and compare with an uncached reference build.

# Cargo build-script execution cache: first verified restore trial

This document retains the earlier uncommitted prototype trials. The validated opt-in implementation is now described in [build-script-cache.md](build-script-cache.md); each historical timing below still refers to its own frozen prototype, not the final accepted binary. It now restores ring's flat native output bundle and streams, removing all 24 native requests in warm Harness builds. The three warm pairs favor Nano, but the median difference is small and the three cold pairs favor kache.

| Phase | Nano median | kache median | Nano pair wins |
| --- | ---: | ---: | ---: |
| Empty compiler caches and clean target | 17.965230 s | 17.067632 s | 0/3 |
| Populated compiler caches and clean target | 1.266634 s | 1.277947 s | 3/3 |

Warm median improvement is 0.89%; cold regression is 5.26%. Individual warm Nano/kache pairs are 1.293183/1.637208, 1.266634/1.277947 and 1.128080/1.169828 seconds. This does not establish a durable advantage or a cold-build win. All warm native objects/archives, rlibs, macro dylibs and script launchers match their own implementation's first cold hashes. Cross-tool byte equality is not asserted.

[Every sample and artifact/source hashes](../benchmarks/harness-build-script-execution.json) records the real dirty Harness adapters snapshot, Rust 1.97.1, kache 1.0.0, eight jobs, offline dependency resolution, alternating cold order and rotated warm order. The workload is the adapters library, not the complete GUI. OS filesystem caches are unflushed. Fetching dependencies and starting/stopping the private kache daemon are outside timing. R2 is excluded. Every Nano cold build records 167 Rust and 24 native misses plus one script execution miss. Every warm build records 167 Rust hits and one script execution hit, with zero native requests.

## Mechanism and current contract

`NANOCOMPILE_BUILD_SCRIPTS_FILE` selects an explicit per-package JSON contract. Mutable input files and directory membership are fully hashed, including absent paths. Installed trees use the existing trusted-installation stamp policy after their initial full content fingerprint; they now follow directory links, record link selection and resolved contents, and validate link and target state before reuse. Caller environment, script binary, contract bytes and selected compiler/resources enter identity. Output restoration reuses ordinary verified content blobs and replays complete stdout/stderr.

A first attempt bypassed linked SDK directories. A later attempt marked membership dependencies as regular files, which rejected ring's large graph in parallel hashing. Both are corrected in this measured prototype. The real Cargo regression fixture covers a graph above the parallel threshold, preserved-mtime source edits/reverts, installed target edits, link retargeting, directory membership, environment changes, stdin, exit codes, jobserver descriptors, nested outputs and corrupt receipts/blobs.

This contract requires deterministic script behavior from declared file contents, environment and declared tools, writes limited to OUT_DIR and streams, and no outstanding background writers. Clock, random, network, metadata-dependent behavior or executable-basename-dependent behavior is outside this experiment. Arbitrary stdin is not cached. Mutable symlinks and non-regular inputs are refused. Outputs must be flat regular files, below the file-count/size bounds, and OUT_DIR must start empty. Unsupported cases execute rather than partially restoring a tree.

The diagnostic ring contract tracks package bytes, local headers and selected Apple compiler/SDK resources. It does **not yet enumerate all archiver/helper executables**. The observations apply to this unchanged machine/tool installation; before promotion, declare and verify the exact archive/helper selection and its dependencies. Do not use this contract as a general toolchain-change correctness guarantee.

## Real edits and SDK fingerprint follow-up

The original measured execution prototype completed [18 real Harness builds](../benchmarks/harness-build-script-source-edits.json), including fresh empty-cache verification builds at each edited state. The linked probe produced 300 → 301 → 312 → 300, and all six wrapper verification builds matched their retained-cache state's rlibs, macro dylibs, script launchers and native artifacts. The original human source hashes remained unchanged. Single timed edit observations favor Nano: leaf 7.742974 versus kache 8.355994 seconds; shared 9.749257 versus 10.275184; revert 1.058342 versus 2.153231. These are single observations, not repeated edit-performance medians.

The [SDK phase profile](../benchmarks/installed-tree-profile.json) measures seven alternating empty-cache installed-tree pairs on the same SDK. The original implementation's median is 839.801 ms; a candidate that stores one whole-tree record and directly hashes every initial file takes 100.527 ms. Warm stamp/link validation is 8.167 versus 8.114 ms. Every fingerprint is identical between implementations. This establishes a reduction in the measured fingerprint phase, not a whole-build speedup. Both retain the complete link/file/directory stamps and full post-hash validation. The candidate passed the same Cargo fixture, including its large graph and link/edit/corruption checks.

The [single-tree tracked patch](../benchmarks/experiments/build_script_execution/single-tree.patch) is against revision `a505ba05b8f1a0eafbc72274ef35de910f0392ec`; pair it with [this script source](../benchmarks/experiments/build_script_execution/single-tree-build-script.zig). Nano's cold median is 17.321950 seconds versus kache's 16.919719 (one pair win out of three); warm is 0.931182 versus 1.186830 (three wins). ## Remaining cold identity cost

[Five isolated Rust identity measurements](../benchmarks/rust-cold-identity-profile.json) show a median of 822.263 ms for an empty cache, versus 1.015 ms for a warm memo. The installed compiler is identical in every measurement and every resulting fingerprint matches. The cold identity creates 360 file memo entries with about 1.24 GB of summed file sizes; this includes separately keyed records and is not a unique-byte or syscall-I/O count. The next cold experiment should profile parallel initial resource hashing after the compiler/resource selection is known, keeping every byte and final stamp check, and validating the identical complete fingerprint before full Harness comparisons.

The [current hardening patch](../benchmarks/experiments/build_script_execution/hardening.patch), against `e1505c0`, plus [its script source](../benchmarks/experiments/build_script_execution/hardening-build-script.zig), adds `internal-rust-identity /absolute/path/to/rustc`. It also propagates restore I/O errors rather than executing over partially restored output, and keeps a successful script's exit status when cache storage fails. [The Cargo fixture passed](../benchmarks/experiments/build_script_execution/hardening-fixture-results.json) on binary SHA-256 `60a7ed9cba39bfd60dfb4f264cd0636c8cddcba4f6faea41a740fe59671b27c2`. These error paths still need specific failure injection before adoption. The profile is diagnostic; no parallel Rust resource optimization or cold superiority is established yet.

## Atomic restoration and explicit archive helpers

The next opt-in prototype includes `tools` for PATH-selected executables and `apple_tools` for helpers selected by a live `xcrun --find` query. On macOS, Apple helpers must be thin Mach-O executables whose startup loads are ordinary absolute system paths; rpaths, external libraries, weak/re-export loads and loader overrides cause fallback execution. Declare helper resources and dynamically loaded dependencies as inputs too. The contract remains an explicit promise about deterministic contents and effects; it does not discover arbitrary script reads.

Restoration now verifies the original output paths and all input/blob evidence, materializes every flat output into a private sibling directory, preserves the original OUT_DIR permissions, then atomically renames the complete directory over the empty OUT_DIR. Streams are replayed only after publication. A staging or publication I/O error fails the invocation and removes staging; it never reruns a script over partial restored files. Unsupported output shapes still execute normally. Successful real execution remains successful if writing the cache fails.

The [real Cargo failure fixture](../benchmarks/experiments/build_script_execution/atomic-fixture.py) passed on binary SHA-256 `4fa6dec16814502c35969c7b6a9bf127122091f4bb7036fedcd4b28e304e98be`; [all checks and runner hash](../benchmarks/experiments/build_script_execution/atomic-fixture-results.json) are retained. It checks two restored outputs, forces a staging permission failure, verifies empty OUT_DIR and absent replay, then verifies a successful subsequent hit and preservation of directory permissions. Unit tests and the real Rust/Zig integration suite also passed locally. This is still a runtime prototype.

To reproduce, apply [atomic-restore.patch](../benchmarks/experiments/build_script_execution/atomic-restore.patch) against accepted commit `ca672e073b66e9d470bad0281bfa21d898382d29`, copy [atomic-build-script.zig](../benchmarks/experiments/build_script_execution/atomic-build-script.zig) into `src/build_script.zig`, and run the archived fixture with a stable Zig 0.17.0 ReleaseFast build. Use [the explicit Harness archiver contract](../benchmarks/experiments/build_script_execution/atomic-harness-contract.json) for the subsequent comparison. These source artifacts are separate from the default accepted runtime.

The [atomic-restore Harness session](../benchmarks/harness-atomic-execution.json) completed five alternating cold pairs and three warm pairs. Nano cold median is 16.648595s versus kache 16.741917s (three Nano wins out of five); warm is 1.060007s versus 1.290287s (three wins). Every repeated output set matches its own cold reference. The cold median lead is only 0.56% and is variable; this does not establish reliable cold superiority. The warm lead is 17.85% in this session.

Inspection then found that Apple's archiver can launch `ranlib`, whose startup uses the selected `libLTO.dylib`. This session's contract records the archiver but omits that child explicitly, so its results apply only to the unchanged installation. The [follow-up archive-chain contract](../benchmarks/experiments/build_script_execution/archive-chain-harness-contract.json) additionally records PATH-selected ranlib, the current selected archiver's sibling ranlib, and its libLTO contents. This is a machine-specific contract for this CLT installation; regenerate it when selecting another tool installation and verify all transitively launched helpers and runtime loads. A general automatically proven archive chain is still future work.

The [archive-chain follow-up](../benchmarks/harness-archive-chain-execution.json) completed three alternating cold and three rotated warm pairs. Cold medians are Nano 16.914951s and kache 17.218077s (two Nano pair wins); warm medians are 0.935224s and 1.150663s (three wins). All repeated rlibs, macro dylibs, script executables and native objects/archives match their implementation's own cold references. Cold caches report zero hits; warm Nano restores 167 Rust entries and one script execution bundle. The median leads are 1.76% cold and 18.72% warm for this exact experiment. Cold pair variability and the explicit machine-specific contract still prevent claiming general superiority or promoting arbitrary build-script execution reuse.
